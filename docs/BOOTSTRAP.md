# الإقلاع بأمر واحد (`./apkforge`)

الأمر الوحيد لتهيئة المشروع وتشغيله على بيئة جديدة — عقل الإقلاع
`scripts/apkforge.py` (مكتبة قياسية خالصة، يعمل من أي مجلد).

## خط الأنابيب

```
./apkforge                      (المحرك 2.0.0: تكيفي)
  GIT? → ENVIRONMENT_CHECK → ENVIRONMENT_DETECTED
  → TOOLS_INVENTORIED → COMPATIBILITY_RESOLVED → PLAN_CREATED
  → TOOLS_READY → CONFIG_READY → RUNTIME_READY → DEPENDENCIES_READY
  → DATABASE_READY → MIGRATIONS_READY → SEED_READY → BUILD_READY
  → SERVICES_READY → HEALTHY → ADMIN_SETUP_REQUIRED? → READY
  (الفشل الذريع: RECOVERING → BLOCKED + تقرير AUTO-RECOVERY EXHAUSTED)
```

- كل تشغيل يبدأ ببصمة بيئة واحدة (نظام/معمارية/بايثون/شبكة/ذاكرة)
  وجرد أدوات واحد فقط — لا فحص مكرر أبدًا.
- فحص توافق مسبق قبل أي `pip`/`npm`: عجلات PyPI مقابل
  (المفسر/المنصة/`requires-python`) مع مانعات صريحة لا تخمين.
- التشغيل **idempotent** مع استئناف حقيقي: كل مرحلة محفوظة في
  `.governance/bootstrap-state.json` (مرتبطة بالبصمة) ولا تُتخطى إلا
  بتحقق خفيف ناجح.
- كل إخفاق يُسجَّل في `.governance/recovery-ledger.jsonl` (بصمة سبب +
  استراتيجية + نتيجة) فلا تُعاد محاولة فاشلة بعينها — وتغيير البيئة
  (تثبيت أدوات بناء مثلًا) يفتح باب إعادة المحاولة تلقائيًا.
- لا يُعلَن `READY` إلا بصحة حقيقية: عمليات + منافذ + HTTP + قاعدة
  بيانات + ترحيلات + مصادقة سالبة + صفحة واجهة.

## الأوضاع

| الأمر | الأثر |
|---|---|
| `./apkforge` | الخط الكامل + فتح المتصفح على الإعداد أو التطبيق |
| `./apkforge --check` | تدقيق فقط (بيئة/أدوات/توافق/خطة/إعداد/قاعدة/خدمات) بلا تغيير |
| `./apkforge --plan` | عرض خطة الإقلاع التكيفية (إعادة استخدام/تخطي/إنشاء/تثبيت) بلا تغيير |
| `./apkforge gitcare status` | بوابة صحة المستودع (فهرس/أجسام/مصدر) |
| `./apkforge gitcare diagnose` | تشخيص كامل + تقرير `logs/git-recovery/<run>/report.md` |
| `./apkforge gitcare cleanup [--deep --yes]` | حذف المؤقت والكاش فقط (المصدر و`.git` محميان دائمًا) |
| `./apkforge gitcare repair-index --yes` | إصلاح الفهرس التالف مع حفظ الأجسام والتاريخ |
| `./apkforge doctor` | تشخيص شامل للقراءة فقط (بيئة/تشغيل/أدوات/توافق/سجل/نقاط حفظ/قاعدة/واجهة/git) |
| `./apkforge recover` | عرض العائق الحالي ثم استئناف الإقلاع مع الشفاء الذاتي |
| `./apkforge --status` | الحالة والخدمات والمنافذ بلا تغيير |
| `./apkforge --repair` | إعادة الخط مع بدائل الخطوات الفاشلة |
| `./apkforge --reset-dev --yes` | إيقاف + حذف قاعدة التطوير والحالة (يرفض الإنتاج، وينسخ `.env` احتياطيًا ولا يحذف الأسرار) |
| `./apkforge --logs` | ذيول السجلات |
| `./apkforge --stop` | إيقاف الخدمات |
| `--skip-build` / `--no-browser` / `--install-tools` / `--json` | معدِّلات (تخطي البناء، بلا متصفح، جلب Apktool، تقرير آلي) |

## البنية المكتشفة من المشروع (لا تخمين)

| السؤال | الجواب المستخرج |
|---|---|
| نظام التشغيل | أي نظام (يُكتشَف وقت التشغيل؛ Linux/macOS/Windows) |
| الأدوات المطلوبة فعلًا | python3 ≥3.10 وpip وnode ≥20 وnpm (من `requirements*.txt` و`package.json`) |
| الأدوات الاختيارية | java وapktool وjadx (تُكتشَف من `PATH` أو متغيرات `APKFORGE_*`) |
| الخدمات المطلوبة | خلفية uvicorn + واجهة ستاتيكية (لا Postgres/Redis/Celery في المرحلة 1 — ADR-004) |
| محرك القاعدة | SQLite ملفي (`APKFORGE_DB`) |
| الترحيلات | `backend/migrations/001–004` + سجل `schema_migrations` |
| الجداول | users وprojects وjobs وartifacts وaudit وsystem_config (مستعادة من الكود — بلا اشتراكات/مدفوعات لأن المشروع لا يملكها) |
| الخلفية | FastAPI (`app.main:app`) على `APKFORGE_PORT` (8000) |
| الواجهة | Vue مبنية (`frontend/dist`) تُقدَّم ستاتيكيًا على `APKFORGE_WEB_PORT` (3000) |
| التشغيل السابق | uvicorn وnpm يدويًا (تحوَّل تلقائيًا) |

## الوحدات التكيفية (`scripts/adaptive/`)

| الوحدة | الدور |
|---|---|
| `env` | بصمة البيئة وكشف Termux وملف القدرات |
| `tools` | جرد الأدوات مرة واحدة (`REQUIRED/OPTIONAL/PHASE_DEPENDENT`) |
| `compat` | مصفوفة التوافق والفحص المسبق قبل التثبيت |
| `recovery` | تصنيف الأسباب (16 صنفًا) وسجل المحاولات والتشخيص |
| `plan` | بناء الخطة وعرضها |
| `checkpoint` | نقاط الحفظ والاستئناف المرتبطة بالبصمة |
| `gitcare` | تشخيص المستودع وإصلاح الفهرس والتنظيف الآمن |

محرك الشفاء الذاتي: كل محاولة تحمل بصمة كاملة (بيئة + حزمة + إصدار +
استراتيجية + أمر + متطلبات + أدوات بإصداراتها) فلا يُحظَر إلا التكرار
المطابق فعلًا. أي تغيير حقيقي (تحديث Rust، مفسر بديل، تثبيت جديد)
يفتح محاولة جديدة تلقائيًا. الترتيب التكيفي: توفير أدوات/حزم النظام
المكتشفة من السجل ← أصلي ← إصدار متوافق (لا يمس الأصل؛ التثبيت في
`.governance/generated/`) ← مفسر بديل مُتحقق في `venv` مستقل (القديم
يُحفَظ دائمًا ولا يُحذَف) ← نواة دنيا للاختياري فقط مع تسجيل التدهور.
`AUTO-RECOVERY EXHAUSTED` لا يظهر إلا بعد استنفاد كل مسار متغير، مع
قسم `NEEDS YOU` لما يحتاج المستخدم فعلًا.

سلّم استرداد `pip` (بالترتيب): أصلي ← إعادة شبكية ← أدوات بناء
← إصدار متوافق بعجلات ← نواة دنيا بلا إضافات أصلية ← إعادة إنشاء
البيئة (صلاحيات) ← تطهير الكاش (قرص) ← `AUTO-RECOVERY EXHAUSTED`
بتشخيص وخطوة تالية. كل تثبيت ناجح يُتحقق (`import` + إقلاع) ثم يُقفل
في `.governance/requirements.lock`.

Termux أصلي: `pkg` أولًا وبلا `sudo`، وفتح المتصفح عبر `termux-open-url` (يتطلب تطبيق Termux:API، وإلا يُطبَع الرابط لفتحه يدويًا)، عجلات `none-any` فقط، سلالم
`clang`/`rust` عند الحاجة، وتحذير صريح عند غياب العجلات لنسخة بايثون.

## ملاحظات أمانة (انحرافات موثقة)

- نقطتا `/setup/status` و`/setup/admin` **إضافة تراكمية** غير كاسرة
  للعقد v1 (الإصدار ثابت 1.0.0؛ بوابات العقود المجمدة ما زالت خضراء).
- `jadx` لا يُجلَب تلقائيًا أبدًا (حجمه ~130MB) — تعليمات يدوية فقط.
- البذور (seed): لا صفوف بذور عمدًا — أول مدير يُنشَأ عبر صفحة الإعداد.

## إصلاح منطق الاسترداد (المسبار أولًا)

- لا يُطلَق `RUST_MISSING`/`COMPILER_MISSING`/`BUILD_TOOL_MISSING` إلا
  بعد مسبار قدرات حي من نفس بيئة `pip` (المسار + الإصدار لكل أداة،
  والتحقق من داخل المفسر أيضًا). الأداة الحاضرة الفاشلة تُصنَّف
  `RUST_BUILD_FAILURE`/`C_BUILD_FAILURE`/`BUILD_BACKEND_FAILURE`،
  وبدائلها عجلات وإصدارات لا إعادة تثبيت الأدوات.
- بصمة المحاولة على **مدخلات** الاستراتيجية (الهدف: الحزمة المثبتة
  للإصدار، ولا شيء للتثبيت الكامل) لا على التشخيص، فاستحالة تنفيذ
  `pip attempt [native]` مكررة ببصمة متطابقة — يظهر `REFUSE` مفسَّر.
- قبل أول `pip`: مسبار لغات البناء من المتطلبات وتوفير مبكر، ولقطة
  `pip debug` في السجلات. بعده: تنقية كل فشل بالمسبار الحي.
- فرع الإصدار يتحقق بالاستيراد الحي، وعند التعارض يجرّب مرشحًا في
  `venv` معزول (`.governance/venv-candidates/`) ثم يعتمده أو يغذي
  فشله للدورة.
- الذاكرة دورة `ACTIVE/STALE`: المسجلة قبل البصمات أو بعد تغيّر
  الأدوات تُعاد من الصفر مع الاحتفاظ بتلميح الحزمة.
- الاستنفاد حالتان: `RECOVERY_AVAILABLE` عند وجود خطوة فتح بشرية،
  و`BLOCKED` عند انعدام أي إجراء معروف؛ وتقرير الاستنفاد يسرد العقد
  (نُفّذ/فشل/تُخطّي/محظور).

## إصلاح maturin: مستوى Android API

- فشل `Failed to determine Android API level` فئة مستقلة
  (`ANDROID_API_LEVEL_MISSING`) تُفحَص قبل قواعد الصدأ العامة —
  ليست دليل غياب Rust ولا استحالة البناء.
- الاكتشاف تلقائي بلا قيم ثابتة: متغير البيئة الموجود إن صلح، ثم
  `getprop ro.build.version.sdk`، ثم `ro.build.version.sdk` من
  `/system/build.prop`. عند التعذر يُسجَّل سبب دقيق بدل اختلاق رقم،
  ويُسجَّل في السجل: المستوى المختار ومصدر الاكتشاف ومستوى الجهاز.
- الاستراتيجية `native_android_api_level` تُعيد البناء في مرشح
  معزول (`.governance/venv-candidates/<attempt-id>/`) مع تمرير
  `ANDROID_API_LEVEL` لعملية `pip` نفسها فيصل `maturin` أثناء
  توليد البيانات. البصمة تضم بيئة البناء، فالمستوى المختلف
  محاولة جديدة والتكرار المطابق مرفوض.
- الاعتماد بعد التحقق فقط: استيراد `pydantic_core` تحديدًا ثم
  `fastapi/uvicorn/pydantic`، والبيئة القديمة محفوظة حتى نجاح
  الاستبدال. أي خطأ بناء جديد يُصنَّف من سجله كاملًا (linker أو
  compiler أو حزمة نظام) وتُستأنَف الدورة.
- تحليل العجلات: عجلات `linux_*` مرفوضة صراحة على أندرويد (bionic
  ليست glibc) مع ملاحظة توثق الرفض، وكل حكم يسجل المصدر وSHA-256.
  دعم المصادر الخارجية اختياري بالقائمة المسموح بها (`فارغة
  افتراضيًا = لا استشارة خارجية أبدًا`) واستشاري فقط لا يُثبِّت
  شيئًا تلقائيًا. الأولوية لإصلاح `ANDROID_API_LEVEL` أولًا.

## استعادة سياق الفشل والعجلة المبنية لأندرويد

- التمييز بين هدف الاستراتيجية (`package`: فارغ للتثبيت الكامل)
  والحزمة المشخَّصة (`diagnosed_package`: ما كشفه السجل). فقدان
  الثانية كان يُفرغ المرشحين ويُنهي التشغيل باستنفاد كاذب.
- عند الإقلاع يُعاد تحليل دليل المحاولة السابقة (ملف السجل ثم
  `detail`) بالمصنف الحالي: فئة قديمة مثل `RUST_BUILD_FAILURE`
  تتحول إلى `ANDROID_API_LEVEL_MISSING` مع `pydantic-core` متى
  أكد الدليل ذلك. التاريخ لا يُعَدَّل ولا يُحذَف؛ تُضاف نتيجة
  إعادة التصنيف كصف تشخيصي (`reclassify`) لمرة واحدة.
- استراتيجية `android_prebuilt_wheel` (لـ`pydantic-core` على
  Termux فقط، وقبل البناء من المصدر): تكتشف قيد النواة من إصدار
  Pydantic المُحَل، وتختار عجلة تطابق ABI والمعمارية ووسم
  `android_<api>_<arch>` (بحد أدنى API 24 وبما لا يتجاوز مستوى
  الجهاز)، ولا تقبل إلا رابطًا داخل المستودع المخصص، ولا تثبت
  إلا بعد تحقق SHA-256 من digest الإصدار (أو ملف checksum
  موثوق)، ثم تثبيت في مرشح معزول مع `pip check` واستيراد
  `pydantic_core` قبل الاعتماد. أي فشل تحقق = رفض وانتقال
  لمسار البناء.
- توفير مفسر بديل على Termux يسبقه فحص `apt-cache policy`:
  الحزمة الغائبة من المستودعات المشتركة تُسقَط بفكرة فتح دقيقة
  بدل محاولة تثبيت فاشلة، ولا يُضاف أي مستودع خارجي تلقائيًا.

## تقوية محرك الاسترداد (إثبات البيئة والحظر المفسَّر)

- مساعد `subprocess` الموحد (`run`) يدمج البيئة المرشحة فوق بيئة
  العملية بدل استبدالها، فلا تُفقَد `PATH` ولا المتغيرات الحرجة
  أبدًا. كل `pip` معزول يُسبَق بكتلة `BUILD ENV VERIFICATION`
  تثبت وصول `ANDROID_API_LEVEL` إلى طبقتين حقيقيتين (عملية `pip`
  ثم عملية حفيدة تحاكي خلفية PEP 517 حيث يعمل `maturin`) قبل
  أي تثبيت.
- خطأ `unset` رغم بيئة مثبتة الوصول فئة مستقلة
  (`ENV_PROPAGATION_FAILURE`) تتجاوز إعادة التصنيف القديمة،
  وبديلها مرشح `native_android_api_no_isolation` (بعد تجهيز
  `maturin` داخل المرشح) الذي يبني بـ`--no-build-isolation`
  فيتخطى طبقة العزل المعزولة عن البيئة.
- العجلة الموثقة تُثبَّت بقيد حقيقي (`pydantic-core==العجلة` مع
  أحدث `pydantic` يقبلها من PyPI) يُمرَّر لكل `pip` تالٍ، ثم
  يُتحقَّق من `pip show` والاستيراد الحي أن المحلل لم يستبدلها؛
  الاستبدال يُشخَّص `VERSION_INCOMPATIBILITY` أو
  `WHEEL_RUNTIME_INCOMPATIBLE` لا نجاحًا صامتًا.
- لا تُقترَح حزمة خارج الرسم البياني للمشروع أبدًا: أي اسم
  يظهر في السجل (بما فيه الأسماء الوهمية) يُرفَض بحظر مفسَّر
  قبل أي استعلام إصدارات، فلا توجد استراتيجية `installable`.
- الحالة لكل حزمة (`RECOVERED`/`BLOCKED`) لا لكل تشغيل: نجاح
  `pydantic-core` لا يمنع تشخيص الحزمة الفاشلة التالية، و`native`
  محظورة للحزمة المشخَّصة ما دامت بصمة البيئة ثابتة.
- قرار تصميمي (§11): المرشح هو وحدة العمل لا المرحلة، لأن
  `pip install` عملية ذرية لا تقبل التجزئة؛ والتقسيم المرحلي
  (تحقق البيئة ← تثبيت ← استيراد ← `pip check`) مطبق داخل كل
  مرشح مع سطور سجل صريحة لكل مرحلة.
- كل `recover` يكتب تقرير `.governance/recovery-report-<run>.json`
  (بلا أسرار): البيئة وسلسلة الأدوات والمحاولات وبصمات المرشحين
  وحالات الحزم والحاجز الحالي والخطوة التالية.
